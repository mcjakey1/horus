# Horus Find Similar, Settings and the First-Run Model Step (Plan 5 of 6) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Search option B, "Find similar". It is an optional, offline image–text model (Google SigLIP base) that the artist downloads once. It finds references that *look* alike, from a library image, a dropped image or typed words. Its results are labelled "Looks similar" and always kept apart from the technique-based "Related" list.

**Architecture:**
- **A new Rust module family, `app/src-tauri/src/similar/`:**
  - `model`: the pinned model artifact table;
  - `download`: a resumable download with a SHA-256 check;
  - `encoder`: ONNX Runtime sessions, SigLIP preprocessing and the tokenizer;
  - `store`: `embeddings.bin` in the library folder, plus brute-force cosine top-k;
  - `indexer`: a low-priority background worker that embeds references in pausable batches.
- **Thin Tauri commands** expose status, enable, disable, remove and pause, plus the three searches. Progress reaches the UI as Tauri events.
- **TypeScript UI:**
  - a Settings panel with the Find similar section;
  - the first-run step from Plan 1 Task 9, now able to start the real download;
  - a "Looks similar" tab in the Reference view's margin;
  - a "Looks similar" section in the search dropdown;
  - an image drop target.

  None of them exists in the DOM while the feature is off.

**Tech Stack:**
- Plan 1's stack: Tauri 2, Rust (edition 2024), TypeScript and Vite, and Vitest with jsdom.
- New crates (amended 27 Nov 2026 per preflight rulings B1, R2–R5):
  - **Task 1 adds only these two (R5):**
    - `ureq = "3"`, with rustls on ring and no tokio in the client (R3). Task 1 confirms that `cargo tree` shows no `aws-lc-sys` and no `cmake`.

  - **Task 2 adds these two:**
    - `ort = { version = "=2.0.0-rc.15", default-features = false, features = ["load-dynamic", "api-31"] }`, as the Task 0 spike ran it. This is the newest release on crates.io as of 25 Nov 2026. There is no stable 2.x, so pin it exactly. `api-31` matches the pinned Microsoft ORT 1.31.1 (R2: `api-NN` <= the pinned ORT minor version).
    - `tokenizers = { version = "0.23", default-features = false, features = ["fancy-regex"] }`: pure Rust, no Oniguruma C build.
  - **No `ndarray` (R4):** tensors are built with `Tensor::from_array((shape, Vec))`.

## The model artifact (research, checked on 25 Nov 2026)

| | Value |
|---|---|
| Model | Google SigLIP base, patch 16, 224 px (`google/siglip-base-patch16-224`, Apache-2.0). The ONNX export used is `Xenova/siglip-base-patch16-224` on Hugging Face |
| Pinned revision | `4649052661e53c7000355844105f8a1792088239` |
| Vision encoder | `onnx/vision_model_quantized.onnx`: 99,499,129 bytes, SHA-256 `ef14a954f3d57e1806666432bd9785004c1dc27100aa260eee0cb0f10a5de058` |
| Text encoder | `onnx/text_model_quantized.onnx`: 111,475,220 bytes, SHA-256 `ad0329b1f35acc66d8953ff2559ce358da8eb0a7011794cf951523d63a4dbce2` |
| Tokenizer | `tokenizer.json`: 2,398,744 bytes, SHA-256 `4a17c975210be5ab4c36b47d8dae4eefb866dbfb1e676e394aad85dc30a3ae08`. It is a SentencePiece Unigram tokenizer with a Metaspace pre-tokenizer, and `tokenizers` 0.23 reads it. Its normalizer has **no** lowercasing, but `tokenizer_config.json` sets `do_lower_case: true`, `model_max_length: 64` and `pad_token: "</s>"`. So the app lowercases the text itself, then pads or truncates to **64** tokens with `</s>` (id 1). The text model takes `input_ids` only, with no attention mask |
| Preprocessing | Not downloaded: its values are pinned in code. From `preprocessor_config.json`: resize to exactly 224×224 with no crop, which squashes the aspect ratio (bicubic, `resample: 3`); scale by 1/255; mean `[0.5, 0.5, 0.5]`; std `[0.5, 0.5, 0.5]` |
| Embedding size | 768 (`text_config.hidden_size` in `config.json`; SigLIP base vision is also 768) |
| Download total | 213,373,093 bytes (the three downloaded files), shown as "213 MB", inside SPEC §5a's "150–350 MB" |
| URL form | `{base}/Xenova/siglip-base-patch16-224/resolve/<revision>/<path>` |
| URL base | `ModelSpec.base = "https://huggingface.co"` (B3) |
| Licences | The original weights are **Apache-2.0** (`google/siglip-base-patch16-224`), and the model card has no clause restricting deployment. **The export repo `Xenova/siglip-base-patch16-224` carries no licence tag.** Its card only says it is the Google model with ONNX weights. This is a residual risk; see "Decisions". ONNX Runtime is MIT, and its binary bundles third-party code listed in its own `ThirdPartyNotices.txt` (C9). `tokenizers` is Apache-2.0 |

The sizes and SHA-256 values above come from the Hugging Face API's LFS metadata at the pinned revision. The tokenizer was hashed after downloading it.

**Why the `_quantized` (int8) files:**
- ONNX Runtime's CPU execution provider runs dynamically quantised int8 well.
- Its fp16 coverage on CPU is partial.

There is no fp32 parity fixture (R18, user confirmed 27 Nov 2026). The model files are SHA-pinned, so the int8 behaviour is fixed. Task 2's ignored `real_model_semantics` test and Task 8's measured cut-offs cover quality.

**Cost compared with CLIP ViT-B/32.** Patch 16 at 224 px gives 196 image tokens against 49, so encoding an image is roughly four times the work. Task 2 records peak RSS and seconds per image before Task 4 starts, and Task 8 measures indexing at scale.

**ONNX Runtime linking** was decided by Task 0's spike (B1, done): `load-dynamic` with Microsoft ORT 1.31.1.

## Global Constraints

- **Copy (SPEC §5a), verbatim:**
  - **First-run prompt:** "Turn on Find similar? It downloads a 150–350 MB image model and indexes your library in the background. Recommended for machines with 8 GB of RAM or more." The buttons are "Turn on now" and "Not now", and neither is pre-selected. The step also shows "Download: 213 MB · This computer: <N> GB of RAM" (R12: the existing `systemRamGb()` line, with the download size added).
  - **Results label:** "Looks similar", always. Never "Related".
  - **English hint (decision 3):** the "Looks similar" group in the search dropdown carries the subline "Works best in English." whenever a typed query is shown.
- **Off means absent.** While `find_similar` is not `"on"`, the following are not rendered at all (not merely greyed out):
  - the "Looks similar" tab;
  - the dropdown section;
  - the drop target.

  Typed searches call only option A (`api.search`). Nothing else in the app depends on option B.
- **The model:**
  - It is never in the installer.
  - It is stored once per user, at `app_local_data_dir()/models/siglip-b16-224-q8/` (`%LOCALAPPDATA%` on Windows, so it doesn't roam), and shared across libraries (R17). The QA harness names this folder separately from the config folder, so a model can be kept between QA runs on purpose.
  - It downloads only on an explicit "Turn on" (first run or Settings), or when start-up resumes a `.part` download that such a "Turn on" began (B4).
  - That download is the only network access in the app. It is an HTTPS GET of the pinned URLs with User-Agent `Horus/<version>`, and sends no identifying data.
- **ONNX Runtime (B1, R2):**
  - It is loaded with `ort::init_from(path)` only when Find similar is enabled. With the feature off, ORT is never loaded, so nothing else in the app depends on it.
  - A load failure is a caught `Err`: phase `Error`, and `find_similar` set to `"off"`.
  - **Telemetry off:** `ort::init_from(path)?.with_telemetry(false).build()?` runs once, before any session. The returned `Environment` is held alive in a process-wide `OnceLock<Environment>`. (ort keeps only a `Weak`; if it were dropped, a later session would recreate a default environment with telemetry on.) Task 2 has one source-check test for this.
  - `api-31`, matching the pinned ORT 1.31.1 (`api-NN` <= the pinned minor version).
  - **Load rules (Task 0):**
    - `init_from` gets an absolute path to the bundled library only, never a bare name. (Windows' `System32` holds its own ORT 1.17.1.)
    - No `ort` API call is made before `init_from` has succeeded. Any earlier call falls back to loading `onnxruntime.dll` by name and panics, or silently loads the wrong one. So `LoadDynamicError` maps to a `String` or our own error, never to `ort::Error`.
    - One environment per process: check `ENV.get()` first, and serialize the lazy init, so `build()` runs at most once. A failed init leaves Find similar in `Error` until the app restarts.
  - **CPU guard (R1, required):** on x86_64 only (`#[cfg(target_arch = "x86_64")]`; macOS arm64 has no such check), before load, `if !is_x86_feature_detected!("avx2")`, phase `Error` with "This computer's processor can't run Find similar.", and `find_similar` set to `"off"`.
- **Error copy (R11):** every error the artist sees comes from one copy table, `similar/copy.rs`. Raw error text (network, I/O, ORT, HTTP codes) goes to stderr only, never into `SimilarStatus`.
- **Integrity:**
  - Each file downloads to `<name>.part`, resuming with `Range:`.
  - It is renamed into place only after its SHA-256 equals the pinned value.
  - A model directory is loaded only when every file matches (its `.ok` marker).
- **`embeddings.bin` lives in the library folder.** This adds one optional file to Plan 1's folder layout. It is a derived cache, so deleting it only means re-indexing.
- **Image input is `thumbs/1024/<hash>.jpg`.** Originals are never decoded (SPEC §9). A dropped external image is decoded once in memory and never copied into the library.
- **Indexing:**
  - runs at low priority in the background. "Low priority" means exactly the three values below; there is no OS priority API;
  - works in batches of `BATCH = 16`;
  - limits ONNX Runtime to `intra_threads = 2`;
  - sleeps `NAP_MS = 40` between batches;
  - can be paused;
  - never blocks a command for longer than one batch.
- **Scoring:**
  - L2-normalised 768-d embeddings, scored by dot product (cosine). SigLIP's sigmoid training loss doesn't change cosine ranking.
  - Its score **scale** differs by mode, though: text-to-image cosines run much lower than image-to-image ones. So the cut-off is set per model **and** per mode, in `ModelSpec`:
    - `sim_min_image`, provisionally `0.5`;
    - `sim_min_text`, provisionally `0.03`.

    Task 8 calibrates both on the demo set and records the values.
  - At most `SIM_K = 24` results are kept, highest first, excluding the query reference itself.
  - The UI shows "Looks similar" results **in rank order without a number**, because raw cosines across modes would mislead. The numbers stay in the API for tests.
  - `SIM_K`, `BATCH` and `NAP_MS` live in `similar/mod.rs`. The cut-offs live in `ModelSpec`.
- **No auto-tagging (SPEC §5a, §11).** No code path turns a similarity result into a tag or a suggested tag.
- **Execution provider:** the CPU only, in this plan.
- **Platforms:** Windows and Linux x86_64, and macOS arm64 (Apple Silicon) only. There is no Intel Mac build and no universal2 (B2).
- **Board scope (R15):** every "Looks similar" list filters by `store.inScope`.
- **Tests never use the network.** Task 1 uses a local `TcpListener` server with no proxy. CI never runs `--ignored` model tests; they read a hand-downloaded `HORUS_SIGLIP_DIR`.

## Review Focus

1. **The download is interrupted** (the network drops, the app quits, the laptop sleeps). The next "Turn on" or app start resumes from the `.part` file. A partly downloaded model is never loaded. Tested in Task 1.
2. **The server returns the wrong bytes**: an HTML error page, a truncated file, or a file changed upstream. The SHA-256 check rejects it and deletes the `.part`. The status shows "The download didn't finish correctly. Try again." The feature stays off. Tested in Tasks 1 and 5.
3. **The model can't start on this machine** (too little memory, an unsupported CPU, missing runtime libraries). The status shows "Find similar couldn't start on this computer.", or for a CPU without AVX2, "This computer's processor can't run Find similar." (R1). `find_similar` returns to `"off"`, and the rest of the app works. With the feature off, ORT is never loaded. Tested in Tasks 0, 2 and 5.
4. **`embeddings.bin` is stale or damaged** (made by another model, truncated, holding deleted references, or copied from another library). It is pruned or rebuilt, never trusted blindly, and loading it never panics. Tested in Task 3.
5. **The library changes during indexing** (an import, a reference deleted, the library switched or closed, a pause). Nothing is written to the wrong library's `embeddings.bin`. New references are picked up on the next pass. Pause takes effect within one batch. Tested in Task 4.

- **How `download` works**, file by file:
  - It skips a file that is already in place with the right size and SHA-256.
  - Otherwise it appends to `<path>.part` with `Range: bytes=<len>-`. If the server answers 200 instead of 206, it truncates the `.part` and starts again.
  - It hashes the finished `.part` and renames it into place only on a match. On a mismatch it deletes the `.part` and returns `Checksum`.
  - After every file passes, it writes the `.ok` marker last.
